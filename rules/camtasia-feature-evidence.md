# Camtasia Feature Evidence

## Authority

- Apply these directives when interpreting or generating Camtasia structures.
- Treat official feature documentation as behavioral guidance, not a serialized JSON contract.
- Treat community schemas as versioned observations, not a complete TechSmith specification.
- Label a structure as locally observed, third-party observed, or unverified.

## Editing Method

- Implement established timeline changes as staged JSON candidates through the project skill.
- Reuse verified same-build constructors and references before collecting new editor examples.
- Use editor interaction to resolve unknown serialization, perform operations outside verified file contracts, or verify the changed result.
- Keep project JSON, source media, installation resources, and Library metadata as distinct dependencies.
- Do not substitute exhaustive mouse-gesture testing for implementing serialized feature support.

## Unknown Features

- Preserve unfamiliar clip types and keys during unrelated edits.
- For a new feature, use a same-version project containing it or a minimal before/after editor save.
- Follow `skills/camtasia-feature/SKILL.md` when the required serialized shape is unknown.
- Record editor build, OS, format version, source, and playback outcome with each finding.
- Never infer effect category strings, enum values, fonts, or asset dependencies from UI labels.

## Portability

- Verify platform-specific effects and media in the target Camtasia installation.
- Keep Smart Player interactions distinct from pixels exported to MP4.
- Preserve source-level effects, shader definitions, and referenced assets when cloning a feature.
- Do not promote a demo's canvas, track layout, inset style, or editorial choices to universal defaults.
